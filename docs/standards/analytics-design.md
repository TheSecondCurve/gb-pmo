# 数据分析与指标标准方案

> 用法：这是**默认决策清单**，直接采用。每个交付系统都必须落地「指标定义层 + interactive dashboard + Agent 分析端点」三件套，不许裁掉。偏离默认决策必须在项目实例中写明理由。

## 核心原则：口径只有一个真相源

所有指标口径集中在**指标定义层（metrics layer）**定义：页面 dashboard 和 Agent 分析端点都从这一层取数，**禁止**在页面组件、route handler、SKILL.md 里各自手写指标 SQL。同一个「本月回款额」，人看到的和 AI 算出来的必须相等——口径统一靠同一份代码实现，不靠约定。

指标定义层每个指标是一张定义卡：

| 字段 | 说明 | 示例 |
|---|---|---|
| 指标名 | 稳定英文标识 + 中文名 | `monthly_receipts` / 本月回款额 |
| 业务定义 | 一句话说清算什么、不算什么的 | 已到账的回款，不含合同未回款部分 |
| 计算式 | 一段参数化 SQL（唯一实现） | `SELECT SUM(amount) FROM receipt WHERE ...` |
| 可切维度 | 允许按哪些维度分组/筛选 | 业务线、客户、销售、月 |
| 时间口径 | 按哪个时间字段归属期间 | 到账日（非合同签订日） |
| 负责人 | 口径拍板人 | 客户方需求负责人 |

## 指标体系：三个维度域（每个项目按此框架填）

访谈时按三个维度域向老板要指标，每个域至少要有能落地的指标：

1. **业务**：业务量与过程转化——订单数、成交客户数、渠道转化、交付进度。
2. **成本收入**：钱——收入额、回款额、成本、毛利/毛利率、应收账龄。
3. **经营有效性**：效率与健康度——人效（人均产出/人均回款）、周转（库存/资金/交付周期）、复购率、客户流失、资金账龄。

指标从 PRD「经营看板」一节逐条转化而来；PRD 里写不出口径的指标，不允许进开发排期（口径先于功能，见 requirement-collection.md）。

## 实体设计规范：为分析建模预留（所有实体强制执行）

业务实体即维度建模的素材。设计任何实体时必须过这张 checklist：

- [ ] **事实与维度分得清**：业务事件/单据（订单、回款、工单、跟进记录）是事实表——带金额、带业务日期、带维度外键；相对稳定的对象（客户、产品、渠道、人员、业务线）是维度表——事实表一律用外键引用，**禁止把维度信息塞进 JSON 字段或备注文本**。
- [ ] **双时间戳**：每条事实既有系统时间（`created_at`）又有业务日期（如到账日、签约日）；分析默认按业务日期，两者都要有。
- [ ] **金额字段规范**：金额独立成列、单位统一（分/元全项目统一）、币种单一；退款/冲正用独立事实记录抵减，不改原单。
- [ ] **状态用枚举不用布尔/自由文本**：状态机可枚举（如 待回款/部分回款/已回款），状态变化有历史可追溯（关键状态记 `status_history` 或等价机制）。
- [ ] **软删不硬删**：事实记录软删，保证历史分析可回溯、审计可还原。
- [ ] **维度表有名称冗余之外的归属**：每个维度表自带分组属性（如客户属于渠道、人员属于团队），支撑按组聚合。

不建新数仓、不引入 OLAP 引擎：数据量小，分析查询直接跑业务库（SQLite 单进程）；事实表上对维度外键和业务日期建索引即可。**大客户升 PostgreSQL 时再评估**读写分离/列存，届时连同 SQL 端点读判定一起重新设计（见 agent-integration.md）。

## 标配交付物一：Interactive Dashboard（页面标配功能）

每个系统必须有一个数据分析页（导航一级入口），P0 交付：

- **指标卡片 + 图表**：三个维度域的核心指标总览；图表用标准栈的 recharts。
- **可交互**：时间范围切换（本月/近 3 月/近 12 月/自定义）、维度筛选与下钻（点业务线 → 看该线下客户明细）、图表与明细表联动。
- **取数唯一入口**：页面只调指标定义层对应的 `/api/metrics/*` 接口，不在前端拼 SQL、不在 route 里临时写口径。
- **交互规范**：遵循 tech-architecture.md 的前端交互规范（筛选即时生效、loading 态、空态引导）。
- 页面展示指标名 + 中文名 + 口径说明入口（hover/详情可见业务定义），口径对客户透明。

## 标配交付物二：Agent 分析端点（与 dashboard 同源）

在形态 B 的 Agent 接入栈上增加两个端点（鉴权与 PAT 模型完全复用，见 agent-integration.md）：

| 端点 | 鉴权 | 作用 |
|---|---|---|
| `GET /api/v1/agent/metrics` | Bearer PAT（read scope） | 返回指标目录：每个指标的定义卡（名称、业务定义、可切维度、时间口径），让 Agent 先理解口径再取数 |
| `POST /api/v1/agent/metrics/query` | Bearer PAT（read scope） | 按 `指标名 + 维度分组 + 时间范围` 查询，服务端走指标定义层的参数化 SQL 执行，返回结构化结果 |

关键规则：

1. **Agent 查指标必须优先走 metrics 端点**，SKILL.md 里写明「指标类问题用 metrics 端点，明细/自由查询才用 SQL 端点」；指标目录随 skill 版本同步更新。
2. metrics 端点与 dashboard 调用**同一份指标定义层代码**，不存在第二份实现。
3. 指标 SQL 由服务端参数化拼接（维度/时间范围是枚举参数，不拼自由文本），天然免疫 SQL 注入，比开放 SQL 端点更可控。
4. SQL 端点保持开放（补录、临时查询仍需要），但**指标口径以 metrics 端点为准**——Agent 自己用 SQL 算出的指标数与 metrics 端点不一致时，以端点为准并在 SKILL.md 中声明。

## 与既有标准的关系

- PRD：「经营看板」一节按指标定义卡格式填写（见 prd-template.md 第 6 节），它是指标定义层的需求来源。
- Agent 集成：端点复用形态 B 的 PAT/安装器/skill 分发机制，无新增信任面。
- 前端：dashboard 遵守 tech-architecture.md 的交互规范（就地筛选、Toast 反馈、等宽数字）。
- 工程：每个指标的验收标准 = 「dashboard 数字与 metrics 端点数字一致」可写成测试用例，纳入场景编号追踪（见 engineering-standards.md）。
