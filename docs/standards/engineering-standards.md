# 研发标准（需求追踪 TDD + 质量门禁）

> 第一原则：**测试跟着需求文档的结构走，不跟着代码结构走。** 覆盖率的含义首先是"用户视角的需求覆盖"，行覆盖率只是代理指标。抽象自 gb-crm 实践（K28 等），并做了删减与改进。

## 1. 需求追踪（本标准的核心）

### 功能点层级

```
业务线（PRD §1 经营结构）
  └── 场景 S{n}（PRD §4.2，稳定编号）
        └── 验收标准（「当…时，应…」，每条 = 一个测试用例）
```

- PRD 中每个场景有稳定编号 S1…Sn，**一经分配永不复用**，废弃场景保留编号标「已废弃」。
- 验收标准必须可测试：「当…时，应…」句式，写不出来 = 需求没收清，退回访谈而不是硬写。

### 测试与需求的镜像

- 每个 **P0 场景至少一条用户视角测试**：从「触发时机」走到「完成标志」，走真实 API + 真 SQLite 库。测试名带场景编号：`S3: 删除客户需二次确认`。
- 测试文件按**业务模块**组织（与 PRD 章节对应），不按技术分层组织。
- **CI 追踪检查**：脚本三层比对——①PRD 全部 P0 场景编号出现在测试里；②`docs/scenarios.md` 登记的**逐条子验收标准**（S1-1 粒度，含标注「已废弃」的保留编号）出现在测试里；③PRD 场景与 scenarios.md 章节互为镜像。任一缺失即红。这把"需求覆盖率"从口号变成门禁，且子条目不靠手工维护自觉。
- 需求变更顺序固定：**先改 PRD → 再改测试（红）→ 再改实现（绿）**。反着走 = 实现驱动需求，禁止。

### 验收口径

- **P0 场景 100% 有对应测试**是验收硬指标；P1 按需。
- 行覆盖率 ≥80% 只是辅助代理（见 §3），不许拿它替代场景覆盖。

## 2. TDD 契约

- **先写失败测试，再写实现**；测试与实现同一 PR。
- Agent 适配规则（vibe coding 场景的关键防线）：
  - 编码 Agent 必须先运行新测试确认红，把失败输出留在会话里，再写实现；
  - **禁止为凑绿修改既有测试的断言**。认为旧测试错了 → 停下来报告，由人裁决；
  - PR 描述带「红 → 绿」证据（首次 CI 失败记录或会话摘录），PR 模板已固化该栏（`.github/PULL_REQUEST_TEMPLATE.md`）。顺序无法被工具强制，只能靠证据链 + review。

## 3. 测试方式与覆盖率

- **一种主力测试**：Vitest + 每个测试一个临时 SQLite 库 + handler 直调（不 listen、**不 mock 数据库**——SQLite 这么便宜，直接用真的）。用户视角场景测试和权限/边界测试都在这一层完成。
- **端到端**：Playwright 业务旅程（真实 build + 单进程托管 dist/ + 真 SQLite），独立 workflow 跑、不挡合并（设计同 gb-crm K28）；发布前与依赖升级后必跑。
- 前端组件测试**不设为标准层**，仅交互极复杂的组件按需补。
- **补丁型测试文件**（按代码结构而非场景组织的分支补齐文件）允许存在，但每条用例必须挂场景号或显式标注【工程防线】；新增用例默认进场景文件。
- **数据量冒烟**：场景层全是小数据集；至少一条大数据集用例（播种 N 项目/N 任务/N 事件）断言指标端点与组装层在宽松时间预算内完成，防数量级恶化（N+1/全表扫）。
- **测试代码同样受北京时区规则约束**（S19）：测试里算「今天/明天」一律走 `server/db/time.js`（`today()`/`addDays()`），禁止 `new Date().toISOString().slice(0,10)`（UTC 语义，北京凌晨 0-8 点窗口必炸）。
- 覆盖率门禁：v8，聚合四项指标 **≥ 80%**（核心目录）。**只有这一个数字门槛**——安全要求走 §4 必测清单，不再叠第二个百分比。纯声明文件排除需在配置里注释理由。

## 4. 必测清单（每个交付系统固定，验收逐项核对）

- [ ] `can()` 权限矩阵逐格；所有 401/403/越权路径
- [ ] 认证边界：bootstrap（零 admin 缺密码拒启）、令牌过期/吊销/禁用用户联动
- [ ] 迁移幂等（跑两次不出错）+ fresh 库全量迁移后可启动
- [ ] **备份恢复冒烟**：从备份文件重建库 + 启动应用 + 关键查询通过（gb-crm 只测了备份产物，没测恢复——备份的承诺是"可恢复"，这个承诺必须有测试兑现）
- [ ] SQL 端点对抗用例表：注释前缀绕过、`WITH ... DELETE`、多语句、PRAGMA 改连接状态、`SELECTX` 前缀误判、凭据列/sessions 黑名单
- [ ] 镜像对齐进 CI：枚举 ↔ 中文 label 双向对齐；SKILL.md schema 区块 drift check（生成脚本 `--check` 比对，漂移即红——不靠人记得跑）

## 5. CI

固定 Node 版本；`lint → typecheck → test（含覆盖率门禁）→ 需求追踪检查 → drift check`。e2e 独立 workflow、不挡合并。

## 6. Git 工作流

`dev`/`main` 常驻双分支；`feat/`、`fix/` 从 `dev` 拉；PR base = `dev`，CI 绿才合，合后删远程分支；禁直推；发布走 `dev → main`。

## 7. 编号决策日志

每个项目维护 `docs/design.md`，决策逐条编号（K1、K2…），每条记三样：**决策 / 理由 / 推翻了什么旧决定**。任何对标准的弱化或偏离必须成文（范例：gb-crm K28 把"e2e 不挡合并"记为有意的弱化）。AGENTS.md 引用编号，让决策可追溯、可被以后的 Agent 理解。

## 8. 交付项目 AGENTS.md

每个项目仓库根必须有 AGENTS.md，读者**首先是编码 Agent**。最少包含：

1. 工程结构与分层规则（每层职责、禁止跨层）
2. 常用命令（lint / typecheck / test / migrate，照抄可跑）
3. TDD 契约 + 需求追踪规则（本文件 §1、§2 生效）
4. 编码约定：JSON camelCase、epoch 毫秒、金额分、删除 = 软删
5. **明确不要做**（负面清单——比正面清单更能防 Agent 跑偏，范例：gb-crm「不做 JWT / 不做导入 / 不上 Redis」）
