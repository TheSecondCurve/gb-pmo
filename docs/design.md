## K1 密码哈希用 scrypt 替代 argon2id

- 决策：密码哈希使用 node:crypto `scrypt`（N=16384, r=8, p=1，随机 salt），不引入 argon2 原生模块。
- 理由：better-sqlite3 已是本项目唯一原生编译依赖，再叠 argon2 增加安装失败面；scrypt 是内置且强度合格的 KDF。
- 推翻：tech-architecture.md 默认「密码 argon2id」。已在该标准副本标注。

## K2 不引入 ORM，查询层直用 better-sqlite3 prepared statements

- 决策：表结构以 `server/db/migrations/*.sql` 手写维护，启动时按序执行并记录 `migrations_meta`；查询层不引入 Drizzle，直接使用 better-sqlite3 prepared statements，行级 snake_case → camelCase 映射由 `server/db/index.mjs` 统一处理。
- 理由：本产品的 Agent 接口本身就是 SQL（单一 SQL 端点 + SKILL.md 文档化表结构），引擎层与 Agent 层保持同一数据语言，避免 schema 双轨漂移；单进程小库下 ORM 抽象收益有限；少一个依赖链。
- 推翻：tech-architecture.md 默认「ORM = Drizzle」。已在标准副本标注为偏离。

## K3 新增受限 action 端点（Agent 触发）

- 决策：`POST /api/v1/agent/actions`，动作白名单枚举：`trigger_extraction` / `generate_project_digest` / `generate_person_digest` / `push_report`；PAT write scope + 功能角色校验 + 审计。
- 理由：定时/生成类操作的触发不是数据读写，SQL 端点无法表达（PRD D4 用户拍板「SQL + REST，SKILL 里约定好」）。
- 推翻：agent-integration.md「单一 SQL 端点，不做 Agent 专用 REST」。已在标准副本与 PRD 7.3#4 标注。

## K9 机器人指令通道：读自由写收敛 + 事件长连接（S20，v0.11）

- 决策：同一飞书自建应用开通机器人能力，事件订阅用**长连接**（纯出站 wss）收私聊/群@/卡片回调，不新增公网入口、不新增服务，网关随单进程内嵌（`@larksuiteoapi/node-sdk` 懒加载，未安装时明确报错不阻塞主进程）。bot agent = **有界循环**（≤6 轮 LLM / ≤8 次查询）+ 两个半工具：`query`（只读 SQL，护栏与 Agent SQL 端点同源共享，抽为 `server/agent/sqlGuard.js`）、`metric`（queryMetric 口径捷径）、`write`（语义化提议，分发器定性：record 自动生效 / suggest+bind 出确认卡 / trigger 复用 action 白名单注册表，注册表抽为 `server/agent/actions.js` 供 HTTP 端点与 bot 共用）。写路径唯一不变量保持：确认卡点按人限责任人/牵头人/admin，生效走既有 `confirmEvent`（decided_by=点按人）。身份门禁只认 `members.feishu_id`（绑定码仅私聊、凭据不经 LLM）；外部群拒答为安全不变量；`bot_commands` 全审计 + 与定时抽取按 message_id 去重。
- 理由：内网单进程无公网回调面，长连接是唯一零新增部署面；D1 全员透明使读侧零权限面、只读护栏复用即可放开；确认卡使 LLM 写侧错误无害（人核对解析值后才生效）；固定意图目录方案被否决——schema 内省让新信息结构零新增工具即可查（通用、不复杂、自由度高）。
- 推翻：PRD §7.2 推送通道「只发不收」的「不收」——机器人指令通道为双向（推送语义不变，已注记）；「两段式 ≤2 次 LLM 调用」的早期设计约束放宽为有界循环（读侧放开，写侧不变）。

## K11 任务模板并入项目类型 + 立项自定义任务 + 均分倒排（S1/S17/S25，v0.18）

- 决策：**裁撤「任务模板」独立对象**（推翻 v0.5 的类型/模板两对象模型）——项目类型内嵌任务清单（`project_type_tasks`：标题+顺序，v0.6 扁平模型不变），配置台只维护类型一个对象；`projects.template_code` 保留为立项时所选类型编码的快照（历史事实不回改），`createProject` 的 `templateCode` 入参降级为 `typeCode` 的兼容别名（同码解析）。**立项可自定义任务**：`createProject` 接受可选 `tasks`（标题数组），给出即覆盖类型清单实例化（source=manual，允许空清单）；立项弹窗选类型=客户端预填、脏了才提交 `tasks`。**倒排**：`autoSchedule` 开关 + 交付日期 → engine 纯函数按「计划开始（缺省今天，北京日）→ 交付日期」均分填每条任务计划起止（末条=交付日期，开始=上一条截止+1 且钳到自身截止），web 弹窗与 AI 立项提议共用；S25 kind 收敛为四类（模板两类裁撤）、Agent action `create_template` 移除、`draft_template_tasks` 更名 `draft_task_list` 并放开到成员 write scope（立项弹窗起草需要）。
- 理由：v0.6 把模板砍成纯标题列表后，模板对象只剩「几行字符串」的信息量，一个字段不值得一张表+一套 CRUD+一条提议通道；v0.5 拆分所服务的「多类型共用模板」在种子数据里就是 1:1、从未被用，而 AI 起草（S17-9）让复制/重生成一份清单的成本≈0。立项自定义任务与倒排是用户 2026-10-01 拍板：类型清单从「刚性实例化」降格为「预填草稿」更诚实；倒排的日期算术放 engine 确定性完成（LLM 不做算术），且只发生在立项瞬间、随表单/提议整体经人确认——不触碰「不做自动重排期求解器」的负面清单边界。
- 推翻：v0.5「项目类型与任务模板拆分为两个对象（一类型绑定一默认模板，多类型可共用）」；v0.8/v0.9 中模板编辑器/`create_template`/`draft_template_tasks` 的「仅管理员」起草边界（随立项弹窗全员起草放开，配置台页面本身仍仅管理员可进）。

- 决策：飞书机器人与 web AI 助手的编排层收敛为**统一会话管线**（`server/brain/bot/pipeline.js`：斜杠命令注册表〔按 surface 声明可用性〕/ 每日限额 / LLM 解析 / 有界循环 / 出口归一化——管线只返回结构化结果不投递），两个入口退化为薄适配器：飞书侧保留幂等去重、外部群拒答、`feishu_id` 身份映射、未绑定门禁、渠道上下文、卡片构造与投递、bot_reply 回执；web 侧保留会话持久化、消息落库、页面确认渲染。管线信封 `{ surface, platform, chatId, chatType, member, channel?, text, ts }` 承载两入口的全部差异（web 恒有身份、群上下文仅 IM 群聊），与「私聊 bot ≈ web 会话」的语义对齐。随管线统一修三处漂移：①限额口径对称（IM 面只计 `platform != 'web'`，web 面只计 `platform='web'`——此前飞书限额把 web 消息也计入）；②web 引入 `/help` `/new` 确定性斜杠命令（进 LLM 之前、零 LLM 成本，LLM 未配置/额度耗尽可用），`/new` 复用 `bot_context_resets` 水位线（platform='web'、chat_id=会话 id），web 历史装配按消息 `created_at` > 水位线过滤；③`/bind` 仍仅飞书私聊（凭据纪律不变）。
- 理由：两入口编排层约 150 行近似复制（`execTool` 闭包逐字重复），漂移已实际发生（限额口径是接近 bug 的不一致）；「丰富交互」前不收拢管线，每个新命令/新卡片都要写两遍且漂移只增不减。`handleBotEvent`/`sendChatMessage` 对外签名不变（s20 测试 41 处直调、s24 走 HTTP inject，测试契约零改动）；后续新交互能力（命令/卡片/推送）只注册一处、两个入口同时生效。
- 推翻：无核心决策被推翻；v0.11「限额=每成员每日指令数」的隐含口径（不区分入口）细化为按面分计，`chat.quotaPerDay` 与 `im.feishu.commandQuotaPerDay` 语义不变、互不串账。

## K25 对话面确认卡收敛：直改为默认，确认卡只留终态操作（S20/S24/S25/S35 修订 + S4-7，v0.46）

## K45 项目知识库绑定与机器人写页面：贴链接绑定 + 指令触发 + 类型分小节（S61，v0.66）

- 决策：每个项目可绑定一个飞书知识库页面（migration 0027 `project_wiki_bindings` 侧表，project_id 唯一=一项目绑一页，镜像 task_refs 外链存法）。**绑定两路径**——①贴 wiki 链接绑定已有页面：`parseWikiNodeToken` 从 URL 正则提取 node_token → `getWikiNode`（`GET /wiki/v2/spaces/get_node`）验证存在并换出 obj_token（=docx document_id）；②在指定页面下新建子页：`createWikiNode`（`POST /wiki/v2/spaces/{spaceId}/nodes`，obj_type=docx）在父节点下建页后绑定。**写入**——用户「记一下」类指令经 `record_wiki` 工具调 `recordToWiki`：按 eventType 映射小节标题（progress→进展/decision→决策/risk→风险/其他→记录），往绑定页面 `appendDocBlocks`（`POST /docx/v1/documents/{id}/blocks/{id}/children`）追加 `[heading2 小节 + text 内容]`。连接器提炼通用导出的 `feishuApi`（tenant_token + query string 支持），权限不足（403/131006/131004）统一翻成中文指引。

## K46 记到文档必须原文：禁止 LLM 浓缩，抠原文 + 浓缩护栏（S61-6，v0.66 增补）

- 决策：`record_wiki` 的 `summary` 语义从「一句中文」改为「用户要记录的完整原文」——**禁止总结/浓缩/改写，逐字保留所有细节**（数字、时间、范围、待办一项不能丢）。两层保障：①提示词明示「summary 必须是用户原文」（源头引导 LLM 抠原文而非创作）；②工具侧浓缩护栏——`writeRecordWiki` 抠掉用户消息的触发前缀（「记一下/记到文档里/写到知识库」等）得到原文，若 LLM 给的 summary 长度 <60% 原文，判定为浓缩丢信息，直接用原文兜底。
- 理由：用户 2026-10-10 实测发现 LLM 把「今天和万科确认了一期范围——含北门、东门两个出入口…预算上限 48 万，下周三前出方案」浓缩成「和万科确认了一期范围」，关键细节全丢。「记到文档里」的语义是**存档**，不是摘要——文档是要回头查的凭据，信息一旦丢了就再也找不回来。LLM 在对话面有浓缩倾向（被训练成「给简洁回答」），必须在提示词和代码两层都设防。60% 阈值是启发式：原文本就简短时 LLM 原样传递即可（不强制替换），只有明显浓缩才兜底——宁可误用原文（信息完整、至多带个触发语气残留），不可漏信息。
- 推翻：K45 中 record_wiki payload 的「summary=一句中文」引导（那是触发 LLM 浓缩的根源）；record_event 的 200 字截断口径不受影响（事件流摘要 vs 文档存档是两种语义）。

## K61 登录会话长效保持：cookie Max-Age 与服务端 session 同一常量 400 天（≥ 1 年不重登，v0.78）

- 编号注：本条起草于 v0.74 窗口（原记 K53），因搁置至 v0.78 合入——K53 已被 S67「定时任务」集中页占用，顺延改记 K61，内容不变。
- 决策：`SESSION_TTL_MS` 从 7 天改为 **400 天**并从 `engine/auth.js` 导出；登录 `Set-Cookie` 显式带 `maxAge`（秒，由同一常量换算）。此前 cookie 不带 Max-Age/Expires 即浏览器会话 cookie（Safari/Firefox 关浏览器即丢，Chrome 仅在「继续浏览上次打开的页面」下保留），服务端又 7 天硬过期——两层任一到期都把人踢回登录页，所以必须同口径且同源，不允许两处各写一个数。400 天取浏览器对 cookie 有效期的上限（Chrome 104+ 按 RFC 6265bis 草案把更长的 Max-Age 钳到 400 天）：既满足「至少 1 年」含闰年无歧义，也不写一个浏览器会偷偷截短的数。固定自登录起算、**无滑动续期**。
- 理由：用户 2026-10-26 要求浏览器至少 1 年不用重新登录。内网小团队 + D1 全员透明，会话被盗的横向危害有限，而每周重登是实打实的日常摩擦；补偿控制已在：httpOnly + HMAC 签名（防脚本读取与篡改）、服务端 `sessions` 行可即时撤销（登出 DELETE、离职联动 DELETE 并吊销令牌），Agent PAT 面独立 90 天不受影响。
- 不做：滑动续期（需求是「一年内不重登」而非「永不重登」，每请求写库不值当）；「记住我」两档（内网单一场景不需要）；`secure` 标记（内网可能 HTTP 直连，交给反代/部署层决定）；过期 session 行定期清理（一人一次登录一行，体量可忽略，`idx_sessions_expires` 已在）。
- 待办/风险：`updateMember` 改密码只换 hash、**不清退该成员既有会话**——会话拉到 400 天后此缺口放大（密码泄露后重置密码无法逐出已登录的会话），建议后续补「改密即清退该成员全部 session」（管理员重置自己密码时会同时登出自己，可接受）。

- 决策：日常重复执行（每日阅读/巡检类）的项目建模为**常态项目**，四个构件：①`projects.kind`（delivery|routine，立项选定后**不可变更**——两类项目的任务语义/视图/结项规则全然不同，事后互转要迁移任务面与口径，明确禁止比半支持便宜）；②任务行=**模板**：`tasks.kind='routine'`（K40 分类第三档，与 reminder 同法不进 `OPEN_TASK` 口径）+ `tasks.weekdays`（CSV 1-7 周一起算，缺省 `1,2,3,4,5,6,7`=每天；仅 routine 任务可设，≥1 天）——**无状态/计划起止语义**（status/plan 日期 patch 一律 400，行停用走删除），状态字段保留 todo 只为不破既有非空约束；③**每日执行状态独立建表** `task_day_records`（(task_id, day) 唯一，status ∈ done|skip，备注 ≤200 字、操作人、来源）：**惰性 upsert、不预生成实例**——「未做=无记录行」，重置=删行；格子只存差异，7 天×N 任务×常年 的空格子零存储、零对账；④打卡=**记录型事件**（K50 语义）：web 就地生效、机器人面 `checkin_task` 依 K25「人的明确指令直接生效并回执」，不设确认卡。周视图取数 `weeklyBoard`（北京自然周周一锚点复用 `bjWeekStartMs`/S19）按需 JOIN 当周记录，写路径 `setDayStatus` 单事务（upsert/删行 + record 型 progress 事件 + 审计）。
- 理由：用户 2026-10-28 需求——常态项目按「每周一张二维表」管理每日执行。备选方案是「每天把任务重置 todo、完成置 done」复用任务状态机：`tasks.status` 单值无法表达「周三完成、周四未做」，`actual_end_date` 单值无日语义，每天翻转状态还会与 K43 生命周期事件、S59 进展事件、指标口径全面打架；另一备选「预生成每周实例」会持续膨胀 tasks 表且与一次性任务生命周期纠缠。模板+差异记录表对既有口径**零污染**：metrics/brief/晨报/组合页进度全部 `kind='work'` 过滤（K40/K63 已铺好的路），唯一漏点是 `/my`、S66 工作台、任务盘点与风险板未指派计数的内联 SQL——补 `kind != 'routine'` 即可（常态永不完成，计入即永久噪音）。打卡拒绝未来日期（北京日）、允许过去补卡（不设回看窗上限——个人纪律数据，补得越全越好，护栏收益低于复杂度）；不适用星期拒绝打卡（400 带适用日提示），避免「周三任务周二打」的脏数据。结项豁免「全部任务完成」（用户拍板：常态项目手动结项即可，S8 校验只对交付项目有意义——常态任务永不 done，不豁免则永远结不了项）；结项总结必填不变（S29 结束留因原则与项目类别无关）。
- 边界：IM **抽取面不做**打卡自动生效（群聊「看完了」缺明确指令性，误打卡的打扰大于漏打卡的损失；@机器人 对话面已覆盖全部明确指令场景，K50 记录型白名单扩 day_status 留待真实使用反馈）；周视图不生成周报推送/连续打卡统计等衍生能力（先跑通打卡主链）；适用星期改配置不回改历史记录（过去格子按当日记录呈现，属事实留痕）；`task_day_records` 不进 SKILL.md Agent SQL 白名单外的任何写端点（Agent 可经 SQL 直查，写走 action 白名单外无通道——与 K50 一致从严）。前端：常态项目详情页以周视图**替换**「01 进度与排期」区块（甘特对无期限项目无意义），任务面保留但去状态/排期列、加星期编辑；组合页时间线无日期常态项目自然落入未排期组，不另做形态。

## K65 常态项目执行视图三档窗口：窗口数学唯一真相源在引擎，双周全局纪元锚（S69-8，v0.81）

- 决策：S69 的「周视图」泛化为**执行视图**——`span ∈ week|biweek|month`（中央枚举 `boardSpan`），存储与打卡链路零变化（`task_day_records` 本就按天落库，窗口纯视图）。四个构件：①**窗口配置化**：`dailyBoard.js` 内 `BOARD_SPANS` 表驱动（每档 = window(anchor)→{start, days} + shift(start, n)→锚点，加档只加一行配置，无 if/else 散落）；②**双周全局纪元锚**：自 2024-01-01（恰为周一）起每 14 天一期，`biweekStartOf = EPOCH + 14·floor(dayDiff(EPOCH, day)/14)`——连续、确定、跨年不断链。**推翻评估阶段的「当年第一个周一」口径**：各年首个周一之间的间隔不是 14 的倍数，按年锚会在跨年处断出一期不完整的天数，全局纪元锚无此问题（代价：双周「期数」与公历月无对齐关系——本就不需要对齐，打卡按天不按期）；③**导航锚点服务端下发**：响应含 `prevAnchor/nextAnchor`，前端导航只消费锚点不做任何日期推算（改掉 v0.80 前端自行 addDays±7 的重复实现）——窗口数学单一真相源；④**项目级默认窗口**：`projects.board_span`（migration 0036，缺省 week；仅常态项目可设，交付项目设值 400），解析序 = 参数 → 项目默认 → 周；前端视图 Tabs 切换即 PATCH 持久化（WYSIWYG，单控件不另设「存默认」按钮）。月=自然月 1 号~月底（天数 28/29/30/31 如实），月导航用年月算术（y·12+m 整数化平移），不用「±31 天」近似。
- 理由：用户 2026-10-28 需求——常态项目按周管理之外，要双周/月度复盘视角。因建模时按天落库，本需求只是窗口泛化：接口/前端结构本就 days[] 数组驱动，改动集中在窗口计算与宽表格呈现；顺手消除 v0.80 前端重复实现窗口数学的隐患（双周/月窗口若前端也算一遍，两处口径迟早漂移）。
- 边界：不引入「隔周执行一次」类新重复规则（适用星期 weekdays 表达不了也不扩——那是另一种调度模型，需要时另立项）；月/双周宽表格用横向滚动+周一分隔线，不做月历网格布局；`board_span` 不进立项表单（建后详情页一切即所得）；`weeklyBoard` 更名 `getDailyBoard`、`weekStart/weekEnd→start/end`、`weekDone/weekApplicable→periodDone/periodApplicable`（内部契约一次到位，不留别名冗余）。

## K66 快速立项一条链 + 新建页面默认父页回落：明确指令直生效，best-effort 不阻塞（S70，v0.82）

- 决策：两个线上实证的断点一并修。①**默认父页回落**：`wiki.defaultParentUrl`（K47/S62）此前只被「记一下」未绑定的确认卡一条路径消费，而用户习惯语义是「新建一个项目飞书页」——`bind_wiki` 协议要求 LLM 向用户索要 `parentWikiUrl`，导致线上 11 个项目知识页全部人工贴链接建立（且用户手贴的就是已配置的默认父页地址）。现 `bind_wiki` 只给 `newTitle` 时自动回落默认父页建页绑定，回执注明挂载位置。**信任边界核对**：明确的新建指令与既有「给足父页链接直生效」同档（K25），K47 确认卡仅覆盖「记一下」的**隐含**建页（用户意图是记录不是建页），语义不冲突、不新增确认卡。②**快速立项 `/init`**：新群 @机器人 `/init [类型码]`（零 LLM 斜杠，先于未登记群开关分发——`answerUnregisteredGroups=false` 时仍可用）或 write `quick_create_project`，一条链完成 建项目→绑群→建知识页。缺省规则刻意收敛：**项目名=群名**（网关 getChat 顺带 `chatTitle`，缺失时工具内连接器回拉，再拉不到明确报错——不猜名字）；**牵头人=发起人**（恒满足 createProject「管理员或拟任牵头人本人」权限矩阵，要换牵头人立项后走 update_project）；**类型=参数 → `projects.quickCreateTypeCode`（缺省 `custom` 自由创建——空项目锚点，migration 0037 重新启用 0017 停用的该类型；生产用户已手动启用，迁移对齐口径）→ 拒绝并列出全部可用类型**（不猜）。知识页 best-effort：无默认父页/飞书失败/凭证缺失时跳过并回执单列原因，**不阻塞立项与绑群**（外部依赖故障不应挡住内部业务动作）。守卫：群已是专题渠道拒绝（告知已绑项目），防误绑重绑。
- 理由：用户 2026-10-28 需求——「拉群 → @机器人」是新项目开工的自然动作，应一条指令拿到「项目+任务清单+专题群+知识页」全套；线上审计（bot_commands/bot_reply）实证既有断点。斜杠与自然语言双入口：斜杠确定性零成本（新群场景最稳），LLM 面在未登记群上下文里引导发 `quick_create_project`（已登记群维持 `create_project`，不隐式换绑本群）。
- 边界：不做「拉群即自动立项」（必须显式 /init 或明确口令——静默建项目是垃圾项目源头）；`quickCreateTypeCode` 不做保存时存在性校验（立项时校验并明确报错，与类型停用语义一致）；不做自动排期/初始分配（回执提示可说「初始分配一下」，走 S64 既有链）；企微无 getChat/知识库，`chatTitle` 与知识页链路仅飞书面生效。

## K67 常态项目晨报分叉：今日/明日待办盘面 + 「默认归属人」措辞，推送层分叉不动对话面（S71，v0.83）

- 决策：S68 晨报推送在 `morningPush.js` 按 `projects.kind` 分叉，常态项目走专用盘面——【今日待办】（适用星期判定当日适用，逐条带打卡状态 未做/⤴跳过/✓已完成，**未做排前**）+【明日待办】（次日适用纯预览）+【昨日以来动态】（**保留置尾**：常态项目也有 record 事件流，用户未否决，按建议保留）。取数与周视图 `dailyBoard` **同源**（`parseWeekdays`/`ALL_WEEK`/`weekdayOf` 复用同一批助手，`task_day_records` 读当日状态）——晨报不另起一套适用/状态口径。**措辞**：常态任务的责任人展示为「默认归属人：X」，说明行注明「其他成员可协助打卡」；数据模型不动（`responsible_member_id` 列共用，打卡 operator 本就记录实际操作人）——「归属人不是绝对的」是展示层修正，不是权限模型变更。常态版**不经 LLM**：无综述段（数据是确定性清单，没有可综述的态势），purpose=morning 不产用量；交付项目四节骨架与综述原样。**范围刻意收窄**：只改推送层——对话面 `/morning` 斜杠与 morning 动作（S28）维持现状（其 morning.js 块对常态项目的「未完共 N 项」失真为已知遗留，后续如需再立项；推送是每天强触达的噪音源，优先修）。
- 理由：用户 2026-10-28 需求——常态项目群要看「今天该做什么（做了没）、明天要做什么」，交付口径的逾期/开工/未完计数对常态任务全是噪声或错误；晨报是定时强触达，错误数字每天放大。分叉放在推送组装层而非 engine/morning.js，避免动 S28 对话面契约与既有测试面。
- 边界：常态项目推送时刻仍随全局 morningCron（不分项目配置，需要时再立项）；周视图/任务列表的「默认归属人」措辞改造不在本次（用户明确先做方案 A）；打卡状态只读当日记录（明日列纯预览，未来日期打卡本就被 S69 拒绝）。
